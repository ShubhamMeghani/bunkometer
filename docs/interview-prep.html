Part A · Understand the project

1. The 1-minute pitch

Problem. Indian college students have to keep attendance above a cut-off, usually 80%, but the real rules are fiddly: 79.99% fails, medical leave counts as present, tutorials may or may not count, some courses check midsem and endsem separately, and missed labs need makeups. Students guess, and guessing wrong means being barred from exams.

Who it's for. Students on their phones, marking each class in one tap. Classmates can import a shared timetable instead of typing it in.

What it does. For every course and evaluation window it shows exactly how many more classes you can skip ("Can skip 5 more"), or what you must do ("Attend next 4 to reach 80%", "No skips left", "Can't recover in this window · best 71.4%"). It also has a trip planner (Go / Careful / No-go), bulk marking for sick days, a history calendar with stats, CSV export, and shareable timetables.

What stands out.

  • Exact maths. Pass/fail and budgets use integer arithmetic only, checked against a 92,256-case brute-force test.
  • Built from a spec. 52 EARS requirements and 49 acceptance criteria, each mapped to a test.
  • A demo anyone can use. /demo runs with no sign-in.
  • Built to standard. Installable PWA, WCAG AA contrast in both themes, private by design.

Live: https://bunkometer.vercel.app. Evaluators should start at /demo.

2. Architecture and request flow

Flow 1: tapping "Present" on Today

  1. MarkControl in src/components/attendance.tsx calls run({type:"mark", target, status}).
  2. DataProvider.run (src/components/data/DataProvider.tsx):
    • validates on the client with validateMutation;
    • applies the change straight away with the shared reducer applyMutation (an optimistic queue);
    • calls the server action.
  3. mutate() in src/app/actions.ts:
    • parses the input with zod and reads the user from the Auth.js JWT;
    • loadSnapshot(user, activeSemester) (src/lib/db/repo.ts, one batched Neon round trip);
    • validateMutation, then applyMutation;
    • diffSnapshots → writeDiff, written as one db.batch transaction.
  4. On {ok:true} the change is confirmed. On an error, it is rolled back and a toast with Retry appears (R21).

Flow 2: opening Courses

  1. src/app/(app)/layout.tsx (a Server Component) calls getAppData() (src/lib/server/app-data.ts):
    • requireUser(); no user means a redirect to /;
    • getToday(): the IST date, or the test-only e2e_today cookie;
    • listSemesters and loadSnapshot.
  2. The layout renders <DataProvider initial={snapshot}>. CoursesScreen calls the engine's summarizeCourses(), which generates sessions, computes per-window budgets and lab status, and sorts danger first.
  3. CourseCard shows the status chip, the headline, the meter and the metrics.

There's no middleware/proxy. Every signed-in page and action checks the user on the server, which also logs out sessions of deleted accounts (R6).

4. Data model and the key algorithm

Tables (src/lib/db/schema.ts). They cascade from users, so deleting a user deletes everything they own in one statement.

  • users: google_id, email, name, active_semester_id. That's all the personal data.
  • semesters: start_date, end_date, and an optional midsem_date (made optional in v0.5).
  • courses: required_pct, count_tutorials, medical_cap, window_mode, and a case-insensitive unique code per semester.
  • slots: weekly timetable entries (weekday, start time, duration, kind, optional valid-from/to dates).
  • no_class_periods: holidays and exams.
  • sessions: a row exists only for a marked scheduled class, or for an extra class. Unmarked scheduled classes are generated on the fly. (slot_id, date) is unique.

Counts per course and window (SPEC §4.4):

  • H = held (marked present, absent or medical)
  • A = attended (present, plus medical within the cap)
  • R = unmarked classes from today on
  • p = required %

Formulas:

met  ⇔ 100·A ≥ p·H                      (integers: 79.99% fails 80%)
K    = 100·(A+R) − p·(H+R)              (slack, in hundredths of a class)
S    = min(R, floor(K/100))  if K ≥ 0   (skips left)
N    = ceil((p·H − 100·A) / (100 − p))  (classes to attend in a row to get back above p)
cur  = floor(1000·A/H) / 10             (shown truncated, never rounded up)

Status is decided by the first rule that matches:

  1. no classes → none
  2. R=0 → Final meets/below
  3. K<0 → Can't recover in this window
  4. S=0 → No skips left
  5. below now → Attend next N
  6. S≤2 → warning
  7. otherwise → safe

Worked example (SPEC E1). p = 80, H = 20, A = 17 (85%), R = 20.

  • K = 100·37 − 80·40 = 3700 − 3200 = 500, so S = min(20, 5) = 5: "Can skip 5 more".
  • Check: skipping 5 ends at 32/40 = exactly 80%, which passes (≥). A 6th skip ends at 31/40 = 77.5%, which fails.

Split windows. Midsem runs [start, midsem], including the midsem date; endsem runs [midsem+1, end]. Each window must pass on its own. Example: midsem finished at 83.3%, but endsem is 4/6 with 18 left. That gives "Attend next 4 to reach 80%" (N = ceil(80/20) = 4), even though the combined whole-semester number would say "Can skip 3 more".

6. Spec-Driven Development

Order of work: SPEC → ACs → PLAN → tests → code.

  • SPEC.md came first: goal, constraints, data model, the exact formulas with 14 worked examples (E1–E14), and requirements in EARS form ("WHEN … THE SYSTEM SHALL …", "IF … THEN …"). Each requirement is tagged Must or Should.
  • Every acceptance criterion is pass/fail and tagged Unit, E2E, Deploy or Manual. There are now R1–R52 and AC-1–AC-49.
  • PLAN.md split the build into 12 phases, with [AUTO] tasks for Claude Code and [HUMAN] tasks for me (Neon, Vercel, the Google OAuth client, real-device checks). It set the rules: one commit per phase, never push, never read .env.local, and stop only if a requirement or AC must change.
  • PLAN.md's AC table records the status and evidence (test file plus commit) for every AC, and its Build notes log every interpretation call.

Spec changes, and why:

  • v0.2. I accepted all 12 open-question defaults, with two additions:
    • a course that can't reach the requirement even by attending everything shows "Can't recover in this window · best X%" (AC-46);
    • preview, local and E2E use the Neon dev branch, and only production uses main.
  • v0.3. Region correction: Neon was actually in AWS us-east-1, so Vercel kept iad1 instead of Singapore.
  • v0.4. Added R51, a public /privacy page, because Google requires a privacy-policy URL to publish the OAuth consent screen.
  • v0.5. The midsem date became optional. It's only needed for split windows, and new R52 blocks removing it while split courses exist. It shipped as commit c0ad9f6 and is live in production, where the migration (making midsem_date nullable) was applied during the Vercel build.

7. Testing, CI and deployment

Unit tests (Vitest): 115 at SPEC v0.5. They cover:

  • every worked example, and a brute-force sweep of 92,256 cases checking met, S and N against their definitions;
  • the edge cases, trip planner, stats, CSV, validators and the demo seed;
  • a "no clock in the engine" purity test.

E2E tests (Playwright on a production build with a mobile viewport): 40. They cover:

  • every flow, plus user isolation (B gets 404 or "Not found" on A's data);
  • rollback when a save fails;
  • an axe WCAG AA audit in both themes;
  • 360 px layout and 44 px tap targets;
  • PWA offline mode;
  • a scan proving no DB driver or secret name reaches browser JavaScript.

CI: GitHub Actions on ubuntu-24.04 runs lint, typecheck and unit tests on every push, with no secrets needed. E2E runs locally against the Neon dev branch. Tests sign in through a test-only provider and pin "today" with an e2e_today cookie, both of which exist only when E2E_TEST_AUTH=1 and VERCEL is unset.

Deploy: pushing to main deploys on Vercel. vercel-build runs drizzle-kit migrate && next build against that environment's own DATABASE_URL.

Secrets:

  • They live only in .env.local (gitignored) and in Vercel environment variables.
  • .claude/settings.json denies the AI reading .env*, and it never printed environment values.
  • Production evidence:
    • AC-41: /api/health returns {"ok":true,"db":true};
    • AC-42: /api/auth/providers lists only google;
    • AC-43: CI is green on ubuntu-24.04.

8. Real problems hit, and how they were fixed

  1. A test race showed up as a database error.
    • Symptom: the server log showed a foreign-key violation on sessions.
    • Cause: a test finished while its last optimistic save was still in flight. The cleanup then deleted the user, and the late insert failed.
    • Fix: tests wait for the server-action response (clickAndSave). I also check the server log for errors after every full run.
  2. The accessibility audit found broken markup. axe reported <ul> lists on Today wrapping their <li> cards in <div>s. I moved the date label inside the list item, and both themes now pass with zero serious violations.
  3. The test database stopped accepting the password.
    • Symptom: during the UI polish, every database-backed E2E test failed with "password authentication failed".
    • Diagnosis: a script printed only the error class, never the URL. Production was healthy, so it was the local dev credentials.
    • Meanwhile: the tests that don't need the database still ran. Commits waited, because the rule is "full suite before commit".
    • Fix: I updated .env.local, and the full suite went green.

    Also: stale local servers held port 3100, so suites ran against fresh ports.

Smaller ones: TypeScript 7 broke typescript-eslint, so it's pinned to 6.0.3. Auth.js reported the test provider's id as credentials, which a unit test caught; the fix reads options.id.

9. Limitations and what I'd do next

Limitations

  • No Google sign-in on preview deployments (Google doesn't allow wildcard redirect URIs).
  • Offline is read-only; there's no offline queue.
  • India time (Asia/Kolkata) only. Required % must be a whole number.
  • Absences marked ahead of time count immediately.
  • Free tier: Neon sleeps when idle, so the first request after a pause can be slow. The database is in us-east-1, far from India.
  • E2E isn't in CI, because it needs a database. No rate limiting.

Next steps

  • Run E2E in CI against a throwaway Neon branch created per run.
  • An offline queue for marks, using the same reducer, replayed on reconnect.
  • Optional reminders (a non-goal for v1).
  • Move the database and functions nearer India once paid regions make sense.
  • Rate limiting on server actions, and audit logging.
  • Timetable import from the college's PDF.

Product and users

★What problem does Bunk-o-Meter solve?

Students must stay above an attendance cut-off, usually 80%, but the real rules are complicated: 79.99% fails, medical counts as present, tutorials may not count, some courses check midsem and endsem separately, and missed labs need makeups. Students track this in their heads or in spreadsheets and get it wrong. Bunk-o-Meter turns one-tap marking into an exact answer per course and window: "Can skip 5 more", "Attend next 4 to reach 80%", or "Can't recover in this window".

Who are the users, and what are the main scenarios?

The primary user is a student on a phone. Classmates import a shared timetable. Evaluators use the demo. The scenarios come from SPEC §2:

  • first-run setup;
  • marking each day;
  • "can I bunk Friday?";
  • planning a trip;
  • bulk-marking a sick week;
  • handling a missed lab;
  • fixing past days;
  • sharing a timetable;
  • deleting the account.
Why is there a demo, and how does it differ from the real app?

So anyone, including the professor, can try every feature without a Google account. /demo runs the same screens and the same reducer on a deterministic seed frozen at Wed 21 Oct 2026. It has one course in danger, one very safe, and one pending makeup lab. Changes are stored only in localStorage, and a test proves the demo makes no POST requests. Sharing and account actions are disabled there.

SDD and requirements

★What is Spec-Driven Development, and how did you apply it?

You write the specification and pass/fail acceptance criteria before any code, then build and verify against them. SPEC.md has the formulas with worked examples, 52 EARS requirements and 49 acceptance criteria, each tagged Unit, E2E, Deploy or Manual. PLAN.md turned those into 12 phases, each with "Done when" AC IDs. One commit per phase references the R and AC IDs it delivered, and PLAN.md's table records the status and test-file evidence for every AC.

What is EARS? Give an example from your spec.

The Easy Approach to Requirements Syntax: a small set of fixed sentence patterns, such as WHEN (event), IF…THEN (unwanted behaviour), WHILE (state) and WHERE (feature). For example, R19: "IF a user tries to mark a session dated after today as Present THEN THE SYSTEM SHALL refuse." It's testable as written, and AC-15 plus AC-22 test it.

How did acceptance criteria map to tests?

Every AC names its type and the requirements it verifies. Each Unit or E2E AC has a test file named in PLAN.md's AC table, for example AC-2 → tests/unit/engine/budget.sweep.test.ts and AC-32 → e2e/isolation.spec.ts. Deploy ACs were checked with curl and the GitHub API against production. Manual ACs were real-device checks I did and recorded with dates.

Give an example of a spec change and how you handled it.

Making the midsem date optional (v0.5). I logged it in the changelog and updated:

  • the data model: midsem_date became nullable, through a migration that only relaxes a constraint;
  • R7, R8 and R9;
  • a new R52: removing the midsem date is blocked while split courses exist.

Then I added AC-48 (unit) and AC-49 (E2E) and ran the full suite before committing. The maths and existing semesters were unchanged, and a test checks that whole-semester results are identical either way. Another change came from deployment itself: Google required a privacy-policy URL, which became R51.

Architecture and routing

★Walk me through what happens when I tap "Present".
  1. MarkControl calls run() in the DataProvider. It validates the change and applies it optimistically with the shared reducer, so the button lights up straight away.
  2. It calls the server action mutate(). The server parses the input with zod, gets the user from the JWT, and loads that user's active semester snapshot in one batched Neon round trip.
  3. The server validates again (future Present is refused; unknown IDs become "Not found"), applies the same reducer, computes a row diff, and writes it in one batch transaction.
  4. On success the change is confirmed. On failure it's rolled back and a Retry toast appears.
Why Server Actions instead of a REST API?

They keep the database code on the server with no hand-written endpoints or CORS, and they're typed end to end. One generic mutate() action plus a pure reducer means validation and logic aren't duplicated between client and server. The trade-off: no public API for other clients, which isn't needed for v1.

How does the demo work without a backend?

The screens depend only on a Snapshot plus a mutateAction function. Signed in, that function is the server action. In the demo it's a local function that always succeeds, and DemoShell saves each confirmed snapshot to localStorage. The engine and reducer are pure, so the same code runs in both modes. "Reset demo" remounts the provider from the seed.

How does the app know what "today" is?

The server decides it: getToday() returns the Asia/Kolkata date (todayIST, with a unit test at the midnight boundary). The engine never reads the clock; today is passed in, and a purity test forbids Date.now() in engine files. E2E tests pin the date with an e2e_today cookie, which works only in test mode. The demo uses a fixed date.

Features and code

How is the trip planner computed?

planTrip() (in engine/trip.ts) works in four steps:

  1. Clip the range to [max(from, today), min(to, semester end)].
  2. For each course and window, count m, the unmarked countable classes in that range.
  3. Re-run the budget with H+m, A, R−m, which gives the projected best %, skips left and status. Labs in the range would need makeups.
  4. Verdict: No-go if any affected window has K < 0; Careful if any ends in warning or danger, or a lab needs a makeup; otherwise Go.

Nothing is saved, and AC-27 checks that.

★How do split windows work? Where does a class on the midsem date go?

A split course has two windows: midsem [start, midsem], which includes the midsem date, and endsem [midsem+1, end]. Each session belongs to exactly one window by its date, and each window must meet the requirement on its own. So a great midsem record doesn't carry over: in the SPEC example, endsem at 4/6 says "Attend next 4" even though the whole-semester total would allow 3 skips. Since v0.5 the midsem date is optional; a course can only be split when the date exists, and it can't be removed while split courses exist (R52).

How do you keep bulk marking all-or-nothing?

The reducer applies the whole range in memory, and the server writes the resulting row diff with one Neon batch, which runs as a single transaction. If any statement fails, nothing is saved, and the client rolls back its optimistic change. Before confirming, the user sees how many sessions will change and how many existing marks will be overwritten.

How do shared timetable links work?
  • Publish: stores a random token of 16 bytes, base64url (128 bits).
  • Share page: /share/<token> loads only the semester dates, holidays, courses, rules and slots. It never includes marks, the owner's name or email.
  • Import: copies everything under new UUIDs into a new active semester for the importer, as an independent copy.
  • Revoke: clears the token, so the link becomes a 404 saying "This link is no longer active". Deleting the account has the same effect.

Database and algorithms

★Explain the "how many can I skip" formula.

If you skip k of the R remaining classes, you end the window at (A+R−k)/(H+R). That passes when 100(A+R−k) ≥ p(H+R), which rearranges to k ≤ K/100, where K = 100(A+R) − p(H+R). So skips left is S = min(R, floor(K/100)). For example, at 17 out of 20 with 20 left and 80% required, K = 500, so you can skip 5 and finish at exactly 80%.

★Why integer arithmetic instead of percentages?

Floating point and rounding cause wrong answers right at the cut-off. 399/499 is 79.96%, which rounds to "80.0%" but must fail. So every comparison uses integers (100·A ≥ p·H), and the displayed % is truncated (floor(1000A/H)/10), so it never rounds up. SPEC example E13 covers this, and a brute-force sweep of 92,256 cases checks met, S and N against their definitions.

Why not store a row for every scheduled class?

Scheduled classes are derived data: weekly slots minus holidays and exams, within the semester and each slot's valid dates. Generating them keeps timetable edits simple: add a holiday and those classes disappear, remove it and they come back. A session row exists only when a scheduled class has a mark, or for an extra class. A mark on a day that later becomes a holiday is kept but ignored (AC-8, AC-24).

How do you know the maths is correct?

Three layers:

  • hand-computed worked examples from the SPEC (E1–E14), asserted exactly;
  • a brute-force sweep of every H 0–30, A 0–H, R 0–30 and p in {0, 50, 75, 80, 85, 100}, comparing the closed-form S and N with direct enumeration;
  • E2E tests that compare UI headlines with values the engine computes for each fixture.
How does the medical cap work?

Medical counts as attended. If a course has a cap, its countable medical sessions are ordered by date and time across the whole semester. The first cap of them count as attended, and later ones count as absent and are flagged "over cap". With split windows, the cap is used up across both windows in date order (AC-4).

Security and privacy

★How do you stop user A from reading or editing user B's data?

The server never trusts IDs from the browser. Each server action loads only the signed-in user's own active semester (the query is filtered by user_id), validates the change against that snapshot, and writes only rows from its diff. Any ID not in your own snapshot comes back as "Not found". Pages also return 404 for someone else's course. AC-32 proves it: user B gets a 404 on A's course URL, B's replayed request with A's slot ID is refused, and A's data is unchanged.

How are secrets handled?
  • Four variables: DATABASE_URL, AUTH_SECRET, AUTH_GOOGLE_ID, AUTH_GOOGLE_SECRET.
  • They live only in a gitignored .env.local and in Vercel's environment settings, and nothing secret has a NEXT_PUBLIC_ prefix.
  • The database client is imported only from server-only modules.
  • A Playwright test scans every loaded script and all of .next/static for connection strings and secret names (AC-40).
  • The AI assistant was denied reading .env* files and never printed environment values.
How is the test-only login kept out of production?

isTestMode() is true only if E2E_TEST_AUTH === "1" and the VERCEL variable is unset. Vercel always sets it, so even if someone added the flag there by mistake, test mode would stay off. A unit test covers all three cases (AC-14), and I checked production directly: /api/auth/providers lists only google (AC-42).

What personal data do you store, and how is it deleted?

Only Google ID, email and name, plus the attendance data the user enters. Sessions are JWTs, so there are no session tables, no profile photos, no ads, no tracking, and no third-party scripts. Settings → Delete account (type DELETE) deletes the user row, and foreign-key cascades remove every semester, course, mark and share link in one statement. Any other device's session is treated as signed out on its next request. The /privacy page states all of this.

Any less obvious security measures?
  • The CSV export prefixes cells starting with = + - @ with an apostrophe, to stop spreadsheet formula injection.
  • Share tokens are 128-bit random values and are pattern-checked before any query.
  • /api/health returns only {ok, db}, never error details.
  • Server Actions are POST-only and checked by Next.js.
  • Every input is zod-validated, with limits such as at most 20 courses per semester.

Testing and CI

★What's your testing strategy?

A pyramid tied to the acceptance criteria:

  • 115 Vitest unit tests where correctness matters most: the pure engine, validators, CSV and the demo seed. They include the 92,256-case brute-force check.
  • 40 Playwright E2E tests on a production build with a mobile viewport. They cover every user flow, isolation between users, failure rollback, an axe accessibility audit in both themes, 360 px layout, offline PWA, and a secret scan of the bundle.
  • Deploy checks against production with curl, and manual checks on real phones.
Why aren't the E2E tests in CI?

They need a real Postgres database and a test sign-in, and CI was kept secret-free by design (C10): it runs lint, typecheck and unit tests. E2E runs locally against the Neon dev branch, and the build rule was "full suite before every commit". The next step is CI creating a throwaway Neon branch per run.

How did you test accessibility?

@axe-core/playwright runs on every main screen, including the share and privacy pages, in both dark and light themes. It requires zero colour-contrast violations and zero serious or critical issues. Another test measures that every marking button and nav tab is at least 44×44 px and that there's no horizontal scroll at 360 px. Status is never shown by colour alone; there's always text plus an icon.

Scalability and failure scenarios

What happens if the database is down or slow?
  • /api/health returns 503.
  • Signed-in pages can't render, because the server loads data per request.
  • Saves fail; the optimistic change rolls back and a Retry toast appears (AC-23).
  • The demo and the PWA's cached pages still open.

Neon's free tier also scales to zero, so the first request after idle is slower; that's an accepted risk (D7).

What if two devices edit at the same time?

Each save reloads the user's current data on the server and writes a diff, so different changes merge. If both devices create the same scheduled mark at once, the unique (slot_id, date) index rejects one, and that device gets an error with Retry. There's no live sync: the other device sees the changes on reload.

What would break first at 10,000 users?

Per-user data is small (limits such as 20 courses), and each save is one batched read plus one batched write, so the design scales horizontally on serverless. The first limits would be the free tiers (Neon compute hours, Vercel function usage) and cross-region latency to us-east-1. I'd also add rate limiting on server actions and move to paid regions closer to India.

Deployment and cost

How is it deployed, and how do migrations run?

Pushing to main triggers Vercel. Its build runs vercel-build, which does drizzle-kit migrate && next build using that environment's DATABASE_URL: production uses Neon main, preview uses dev. Migrations are additive only; the v0.5 one just relaxed a NOT NULL and a check constraint. I verified the deploy with the health endpoint and the providers endpoint.

What does it cost?

Nothing at this scale: Vercel Hobby, Neon free tier and GitHub Actions minutes are all free, and the spec ruled out paid services and AI APIs. The costs are latency, because the free database sleeps when idle, and region choice.

Trade-offs ("why not X?")

Why a PWA and not a native app?

One codebase, nothing to install from a store, an instant demo link for evaluators, and it fits 1–2 days of build time. The installable PWA (manifest, icons, service worker) opens standalone on Android, which a manual check (AC-45) confirmed. Native apps and push notifications were explicit non-goals.

Why JWT sessions instead of database sessions?

No adapter tables, so less personal data is stored and there are fewer database round trips. The downside is that a JWT can't be revoked centrally, so getCurrentUser() also checks that the user row still exists. Deleting the account therefore signs out every device on its next request.

Why Drizzle and Neon rather than Prisma or Firebase?

Drizzle is a light, typed SQL layer with plain SQL migrations and transactional batch on the Neon HTTP driver, which suits serverless. Prisma is heavier at cold start. Neon gives real Postgres with constraints, cascades and branches (separate dev and main). Firebase's document model would make the relational rules, uniqueness and cascading deletes harder to guarantee.
